# 组织与呈现原则

## 从报告实例提炼的可复用做法

技术简报的优势是具体：先交代入口、调用方向、模块职责、消息契约和失败处理，再谈实现与扩展。场景交接的优势是行动清楚：触发条件、输入、可观察结果、责任、验收及待补材料都在正文。审计报告的优势是追溯：问题编号、证据分层、搜索和抽屉适合大量差距。

将这些做法组合，避免两种失衡：只有抽象结论和指标，看不清怎么做；或者把所有历史细节平铺，读者找不到下一步。

## 正文层级

1. **首屏**：报告对象、版本／范围、核心结论、当前最大阻断。
2. **主体**：真实场景、调用链、同维度对照、职责与验收、本次必做／后续预留。
3. **按需详情**：问题的完整论证、修正建议和直接证据。
4. **附录**：历史背景、术语、方法、来源索引、长材料。

复杂报告增加锚点导航。主体章节保持可读，不把核心决定藏在折叠块里；折叠适合历史和长证据。需要“简报＋完整报告”时使用两个产物，并说明各自范围。

## 图与表

- 调用图必须回答“谁向谁发送什么、通过什么机制、结果去哪里”。实现已证实、设计拟定与待验证的连线用说明区分。
- 默认 `flow` 是有序步骤图，`steps[].edge` 描述当前步骤到下一步的调用。分支、循环和并发拓扑应使用经核验的自定义图。
- 类名、接口、协议、路径、用户指定标签照原文保留；边上使用“本地调用”“HTTP 请求”“回调”等中文，专有协议名称可保留。
- 职责表至少覆盖责任方、工作项和验收；对照表采用相同维度，不把长篇论证挤进单元格。
- 行动说明“做什么、谁负责、依赖什么、怎么验收”；避免“完善”“优化”等无具体对象的行动句。

## 视觉与交互

以中文阅读为主设计字距和行高；用浅色纸面、克制的强调色、清楚的分隔和可辨认的状态。大型标题不要挤占正文，避免重复英文眉题、堆叠指标和满屏装饰卡片。

审计有问题台账时保留搜索、中文筛选、清空和详情抽屉。术语虚线下划线支持悬停和键盘聚焦，完整术语表供触屏及打印查阅。正文锚点和表格在窄屏应仍可读。

打印是一份完整文档：独立输出全部问题、行动和证据，展开附录，隐藏导航和操作控件。浏览器验收要检查实际打印布局，不能只查看 CSS 是否存在。

## 中文化范围

| 应翻译 | 应保留 | 需要解释 |
| --- | --- | --- |
| 结构标题、状态、按钮、空态、错误提示、枚举标签 | 专有名词、协议、代码符号、字段、命令、路径、版本 | 会影响读者判断的陌生缩写或领域术语 |

不要用术语提示掩盖结构文案的英文。`SOURCE_BUILD` 可保留在 JSON；读者看到“源码与构建”。`implemented` 显示“已实现”；`FACT` 类分类显示“当前事实”。
